### ☑ Scheduling is durable: publishes on time; a crash mid-batch resumes without double-posting
Tests with **real worker processes that are really killed** (`tests/crash.test.js`):

✔ worker is hard-KILLED mid-publish (in flight to a slow platform): restart -> zero duplicates

### ☑ Status transitions (queued → published | failed) update only after a verified webhook, in a SocialPostEntry-shaped record
* `published` is written in exactly one place: `applyDelivery` (`src/db/repos.js`), called only from `src/services/webhookService.js` after `verify()` succeeds.
* Tests: `✔ VALID webhook flips status to published (probe 4), and only then` (asserts the entry is still `publishing` after the platform accepted it), `✔ a valid webhook can mark a post failed, with the platform reason recorded`, `✔ at-least-once delivery: a duplicate event is de-duplicated; a late contradictory event cannot un-publish`, `✔ terminal states are final`.
* Record: table `social_posts` (`src/db/migrations/001_init.sql`) — status, platform, ids/URL, timestamps, attempts, error. FlyRank's `SocialPostEntry` type was not provided with the brief, so the shape is my own; noted in the README limitations.
* One deliberate exception, documented: after retries are exhausted the *worker* sets `failed` (the platform never accepted the post, so no webhook can ever arrive). `published` always requires a webhook.
